Pixel Art Image Specifications

This is a reference document rather than a walkthrough. It covers how frame dimensions are calculated, why enlarging must copy the nearest pixel, why transparent padding makes files heavy, and what the background removal tolerance actually controls.

Why a sprite sheet must never be resampled

In pixel art every individual colour carries meaning. A single black pixel defines an outline, and one step of mid-grey decides where the shading falls. For that reason, every tool and engine that enlarges sprite art uses nearest-neighbour scaling: one pixel becomes a block of identical pixels, and the original grid survives untouched.

Interpolated scaling does the opposite, blending neighbouring colours into new ones. The result looks pleasingly smooth, which is precisely the problem in pixel art — outlines soften, faint bands of grey appear that were never in the source, and scaling back down afterwards yields something different from the original. That is why this tool's canvas shows your image at 100% and deliberately does not enlarge it. If you need a closer look, zoom in the browser or in the preview instead.

What each scaling method does to a sprite
MethodPixel handlingFit for pixel art
Nearest-neighbourDuplicates blocks by an integer factorGrid preserved. This is what the tool uses.
Bilinear interpolationMixes colours across edge pixelsNot suitable. Outlines blur.
Bicubic interpolationMixes colours over a wider areaNot suitable. Introduces noise and smearing.
Spatial interpolation (e.g. Lanczos)Adds ringing at the edgesEven tuned carefully, the original grid is lost.

It is worth pointing out where this rule is actually enforced. The index.html inside your ZIP renders frames with image-rendering: pixelated, and the preview box is capped at 400px wide with the aspect ratio preserved. Even when the display shrinks, the grid stays crisp; and if the source is larger than 400px it may appear clipped, which is a limitation of the display box and not of the data — the PNGs are stored at full size.

Working out frame size

Once the split counts are known, one frame's dimensions come from two divisions.

frame width = sheet width ÷ columns
frame height = sheet height ÷ rows

If the sheet does not divide evenly, leftover pixels on the final frame can make that one slightly smaller. In equal mode the margins deal with the leftover area, while manual mode lets you type boundary coordinates directly and get identical frames regardless of the frame count.

The status bar summarises this as Total: W × H px • Region: W × H px (top: n, bottom: n, left: n, right: n) • 1 cut: W × H px • N total (C×R). Adjusting a margin can appear to change the frame size, but what really happens is the region narrowing. All frames remain the same size as each other. In manual mode the bar gains a manual adjustment label and shows the 1-cut size as a min-to-max range; a non-zero spread is a signal that the boundaries are uneven.

Packed sheet or loose frames

The tools here produce both shapes of output: frame PNGs bundled in a ZIP, and — in the GIF tool — a single sheet PNG with every frame composited together. Which one suits you depends entirely on what your engine reads.

Packed sheet versus individual frames
CriterionOne sheet PNGMany frame PNGs
Texture loadingA single read; fastest.A file per frame must be opened.
Engine setupYou must declare sheet size and grid counts.Filenames alone convey the order.
Replacing one frameThe whole sheet must be rebuilt.Swap that single file.
File countOne.Grows with the frame count.
Build scriptsReproduce the packing rule exactly.Works as-is.
GPU memoryThe full sheet occupies memory at once.Only the frames you draw are resident.

In short, ship a packed sheet when the asset goes out with the game and is loaded once; keep loose frames when you need to tweak individual poses across a growing set. The GIF tool offers a third option by re-saving the animation as a GIF, which is useful when the animation must survive outside an engine. That workflow is covered in the GIF conversion guide.

File size and memory

The output format is always PNG. It is lossless, so pixel values survive untouched, and it supports transparency. There is no JPG or WebP option. WebP would be smaller, but uneven support across browsers and engines still makes it a risky choice for sprite data, and JPG has no alpha channel at all, ruling it out whenever a transparent background is needed.

PNG is lossless, which means even a slight colour change is stored as a different value. A sheet with large semi-transparent areas — artwork sitting on a very light outline, for instance — therefore ends up larger than expected. The bigger problem is completely invisible empty space. There is no marker inside the PNG that lets it skip runs of fully transparent pixels, so every one of them is stored. Large gaps between frames change nothing visible while steadily inflating the file. That is why trimming the margins in equal mode is more than cosmetic housekeeping.

There is no frame-count limit coded into the tools. The remaining constraint is device memory, so two figures are worth checking before you start.

What to verify before a large batch
CheckQuestion to ask
Total sheet pixelsDoes width × height fit in device memory and under the engine's maximum texture size?
Per-frame sizeIs it a whole number, and logically sensible next to the size you will draw it at?

How colour and tolerance interact

Background removal picks a colour and deletes pixels close to it. The tolerance slider decides how close counts as close, and the two tools give it different ranges.

Tolerance ranges by tool
ToolRangeDefaultRe-applied after
Grid cutter0% ~ 30%10%200ms debounce
GIF sprite splitter1% ~ 50%10%150ms debounce

Low values remove conservatively and keep the sprite body intact; high values remove more broadly and clear backgrounds cleanly. The upside is leftover background that fails to disappear; the downside is similar colours inside the character disappearing with it. Start from the 10% default, inspect the result with your own eyes, and adjust from there.

In the grid cutter, switching the toggle off restores the original image exactly, so a mistaken removal costs you nothing and several values can be compared quickly. In the GIF tool a more generous tolerance is often natural, because many frames share the same thin background colour. The detection method and the tolerance behaviour are explained in more detail in the background removal guide.

Tolerance is calculated as a distance across RGB values. The same input produces the same result on any device and at any time, so you can compare values by eye as you adjust the slider and settle on a good setting quickly.

Pre-export checklist

  1. Is the 1-cut size a whole number with no variation between frames?
  2. Is unnecessary transparent padding gone from between frames?
  3. Is the frame size within the engine's maximum texture dimension?
  4. If the animation skips frames, does the total count match the intended order?
  5. If background removal was used, are small features like outlines and pupils still intact?
  6. Is the output really PNG?
  7. When enlarged, are the seams between frames visible?
  8. If it is an animation, have you checked the real playback speed with index.html?
